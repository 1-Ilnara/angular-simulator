# Signals и resource(): ответы на устные вопросы

1. **Signal** — обёртка над значением, которая сообщает Angular, кто и когда это значение читает. Решает проблему «как Angular узнаёт, что данные изменились», точечно: обновляются только те места шаблона, которые прочитали этот signal. Обычное свойство класса «немое»: Angular о его изменении не знает, ему нужен Zone.js или ручная пометка.
2. `signal(0)` создаёт хранилище значения. `count()` читает значение и, если чтение идёт внутри computed, effect или шаблона, регистрирует читающего как зависимого. `count.set(5)` записывает новое значение; `count.update(v => v + 1)` считает новое значение из старого. Если значение изменилось (сравнение `Object.is`), все зависимые помечаются на пересчёт.
3. **Dependency tracking** — Angular во время выполнения computed/effect запоминает, какие signals были вызваны (прочитаны) внутри. Только они становятся зависимостями. Зависимости пересчитываются при каждом запуске: что не прочитали в этот раз, отслеживаться не будет.
4. `computed()` — чистое вычисляемое значение, только для чтения, пересчитывается лениво. `effect()` — побочное действие (лог, запись в localStorage, вызов не-Angular библиотеки), запускается при изменении зависимостей. computed для производных данных, effect для действий. **Неправильно:** в effect делать `this.total.set(this.a() + this.b())`, то есть вручную синхронизировать один signal с другим. Для этого есть computed (иначе лишние циклы и ошибки).
5. **Memoization:** computed запоминает последнее значение и пересчитывается только если изменилась хотя бы одна его зависимость И кто-то прочитал значение. Если ничего не изменилось, возвращается кеш. Нужна, чтобы тяжёлые вычисления не повторялись зря.
6. В effect все signals, прочитанные при запуске, становятся зависимостями. `untracked(() => ...)` — прочитать signal внутри effect/computed, **не** делая его зависимостью (например, прочитать значение для лога, но не запускать effect при его изменении).
7. Если signal прочитан в шаблоне, шаблон становится зависимым, и при изменении значения Angular сам помечает этот компонент для проверки, даже при OnPush. Поэтому OnPush + signals работает без `markForCheck()`.
8. Observable — поток значений во времени (события, запросы, отмена, debounce, комбинации операторами). Signal — «текущее значение» с синхронным чтением, без подписок. Signal выбираю для состояния UI и производных данных (счётчики, фильтры, итоги). Observable — для асинхронных потоков и сложной логики: debounce, switchMap, retry, WebSocket, совмещение источников.
9. `toSignal(obs$)` превращает Observable в signal (подписывается и отписывается сам), `toObservable(sig)` наоборот. У `toSignal` без `initialValue` до первого значения signal равен `undefined` (тип `T | undefined`), и это надо учитывать в шаблоне; опция `requireSync: true` годится только для Observable с синхронным первым значением (как BehaviorSubject), иначе будет ошибка.
10. `fullName` — computed: ленивый. Пока его не прочитали, он не считается вообще (0 раз). При первом чтении пересчитается 1 раз. Дальше пересчитывается только после изменения `firstName` или `lastName` и только когда его снова прочитают. Если оба изменили до следующего чтения, будет один пересчёт.

# resource()

**Зачем.** Signals отлично описывают синхронное состояние, но данные с сервера асинхронные. `resource()` связывает их: «когда signal-параметры изменились, сам выполни запрос и дай мне результат в виде signals».

**Что даёт:** `value()` (данные), `isLoading()`, `error()`, `status()` (idle / loading / reloading / resolved / error / local), `hasValue()`, `reload()`, а также `set()`/`update()` для локальных правок.

**Основные формы.**
- `resource({ params, loader })`: загрузчик на Promise (например, `fetch`), получает `params` и `abortSignal`.
- `rxResource({ params, stream })`: то же, но загрузчик возвращает Observable (подходит для HttpClient и интерсепторов).
- `httpResource(...)`: запрос через HttpClient, прямо по URL-signal.

**Реакция на параметры.** `params` — функция, читающая signals. При изменении любого из них resource запускает новый запрос, а предыдущий отменяет. Если `params` вернул `undefined`, запрос не выполняется (состояние idle).

**Отличие от HttpClient + RxJS.** Меньше шаблонного кода: не нужны `subscribe`, `switchMap`, отдельные loading/error-флаги, отписка. Результат сразу в signals, которые хорошо работают в шаблонах и с OnPush.

**Заменяет ли RxJS?** Нет. Это замена для простого сценария «параметры поменялись, загрузи данные».

**Когда resource:** загрузка данных по параметрам (страница, фильтр, id), показ loading/error, перезагрузка по кнопке.
**Когда RxJS:** debounce, throttle, `retry` с логикой, объединение нескольких потоков (`combineLatest`, `forkJoin`), WebSocket/стримы, сложная очередь запросов, отмена и приоритеты. Поэтому в домашке debounce для поиска сделан через RxJS (`debounceTime`), а запрос выполняет `rxResource`.

**Ограничения.**
- API resource долго был экспериментальным: проверь его статус в документации твоей версии.
- Нет встроенных debounce, retry, кеша между вызовами.
- При смене параметров `value()` очищается (пока грузится новое), и нужно самому хранить «прошлое» значение, если надо избежать мигания (в домашке для `total` использован `linkedSignal`).
- Хранит только последний запрос.
